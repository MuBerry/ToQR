# fnos-qrcode —— 飞牛 fnOS 原生应用包（FPK）

把「二维码批量生成器」打包成飞牛 fnOS 的原生应用：应用中心里手动安装 `.fpk` 即可，
装完在桌面出现图标，点开就是二维码批量生成页面。

- 默认端口 **10001**，**安装时可指定**，**装好后可随时改**
- 用户认证**可选**（安装时和装好后都能开关）
- 纯 Python3 标准库实现，不需要 node、不需要 Docker、不需要联网装依赖
- v1.0.4：登录失败锁定逻辑调整——计数改为按**来源 IP**统一累计、**取消内网豁免**
  （局域网内锁定真正生效）、新增 **120 秒连续失败窗口**避免误锁；倒计时位置与刷新恢复不变
- v1.0.3：按第三轮渗透测试报告做安全加固（提示信息、CSRF、安全响应头、请求层防护），
  并修掉「打包下载 zip 在真实部署上必定失效」的 CORS 问题
- v1.0.2：修掉登录限流的两处毛病（倒计时不动、等待后仍显示同一秒），锁定时间 60s → 120s
- v1.0.1：修掉「不管把端口改成什么，启用时都报端口被占用」——见「已知限制」第 2 条

## 构建

**推荐：在飞牛设备上构建**（官方 `fnpack` 会做完整校验）

```bash
# 把 fpk/ 整个目录拷到 NAS，然后在 fpk/ 里执行
fnpack build
# 产出 fnos-qrcode.fpk
```

fnOS 自带 `fnpack`（`/usr/local/bin/fnpack`），无需额外安装。

**没有 fnOS 时**，`build-fpk.sh` 会自动回退到内置打包器（`tools/build_fpk.py`，
按 fnpack 产物结构生成同构的 `.fpk`）：

```bash
bash build-fpk.sh          # 构建
bash build-fpk.sh --list    # 只列打包清单
```

两者都会先把仓库根目录的 `index.html` 同步到 `app/ui/index.html`，保证页面只有一份源。

## 安装

### 方式一：Web UI（推荐，能看到向导）

1. 应用中心 → 左下角**设置** → 打开「**手动安装**」
2. 应用中心 → 左下角「**手动安装**」→ 选择 `fnos-qrcode.fpk`
3. 按向导填写：

   | 向导项 | 默认 | 说明 |
   | --- | --- | --- |
   | 服务端口 | `10001` | 1024~65535，不能与其他应用冲突 |
   | 是否开启用户认证 | 不开启 | 开启后访问本应用需先登录 |
   | 登录用户名 | `admin` | 仅在开启认证时生效 |
   | 登录密码 | 空 | 至少 6 位；开启认证时必填 |

4. 安装完成后在应用中心点「启用」；桌面随即出现「二维码批量生成器」图标

### 方式二：命令行

```bash
cat > /tmp/install.env <<'ENV'
wizard_port=10001
wizard_auth_enable=off
wizard_auth_user=admin
wizard_auth_pass=
ENV

sudo appcenter-cli manual-install enable       # 首次需要打开手动安装开关
sudo appcenter-cli install-fpk fnos-qrcode.fpk -e /tmp/install.env -v 1
sudo appcenter-cli start fnos-qrcode
```

> 带向导的应用**卸载**必须走 Web UI（命令行会提示 `please uninstall it from Web UI`）；
> 升级同样是卸载后重新安装。

## 装好后调整配置

桌面图标**右键 → 管理应用 → 应用设置 → 运行设置 → 编辑**：

- **服务端口**：改完点「保存并重启」，应用自动重启并用新端口；桌面图标的访问端口会同步跟随
- **用户认证**：下拉切换开启/关闭；用户名、密码留空表示保持原值，填写则覆盖

这两个字段来自 `wizard/config`，与安装向导用的是同一套字段名（`wizard_port`、
`wizard_auth_enable`、`wizard_auth_user`、`wizard_auth_pass`），所以升级时可以平滑迁移。

## 实现要点

**端口如何做到「安装时可指定、装后可改」**

- 真实端口只存在一处：`$TRIM_PKGETC/settings.json`（`$TRIM_PKGETC` 走应用配置目录，升级不丢）
- 向导字段由生命周期脚本 `install_callback` / `config_callback` 写进该文件，写完按需重启
- `app/ui/config` 里入口端口写成 `${wizard_port}` —— 这是应用中心的运行时变量，
  所以桌面图标的地址会自动跟着向导里的端口走，**不需要重建包**
- `cmd/main` 启动时用 `app.py --print-port` 读取实际端口，`--check` 用来确认端口真的起来了
- **但应用中心启动前的占用检查只认已安装 manifest 里的静态 `service_port`**，
  不认 `${wizard_port}`。所以本包 `checkport = false` 关掉该检查，
  同时 `install_callback` / `config_callback` / `upgrade_callback` 会用
  `sync_manifest_port()` 把那儿同步成真实端口，让声明和实际一致

**认证如何实现**

- 密码以 `pbkdf2_sha256`（20 万次迭代 + 随机盐）存哈希，**明文不落盘、不进日志**
- 登录成功后下发 HMAC 签名的 Cookie；会话密钥由密码哈希派生，
  因此服务进程不需要写配置目录，避开安装脚本（root）与运行用户（package）权限不一致的坑
- 未登录访问任意路径 → `302 /login`，拦截发生在**文件解析之前**，
  所以访问不存在的路径同样是 302，无法未授权探测站内文件
- 登出会吊销该会话（进程内吊销表），复制走的 Cookie 立刻失效
- 登录表单带**一次性 CSRF 令牌**（服务端保存，不引入预认证 Cookie），提交即作废
- 登录失败限流（v1.0.2 起锁定 120 秒，v1.0.4 起按来源 IP 记账）：
  同一 IP 在 **120 秒内连续**失败 **5 次**后锁定该 IP **120 秒**；
  锁定期间在登录按钮下方实时倒计时，秒数由服务端渲染，刷新后仍准确恢复；
  锁定期内的重复提交**不会**延长锁定窗口，锁定到期后失败计数清零、重新给满额机会；
  错误提示统一为「用户名或密码不正确」，**不透露**剩余可尝试次数

**为什么锁定期内的失败不重置倒计时**

早期实现里 `fail()` 每命中一次就把 `until` 推后一整轮，于是「等一会儿再试」看到的
仍然是 60 秒——用户感知就是「倒计时永远卡住」。现在 `until` 只在**首次越界**时设置，
锁定期内只累加计数，语义变成「从第 5 次失败起算，120 秒后放行」，等待才是真的有效。

**锁定粒度：按来源 IP（v1.0.4 调整）**

v1.0.3 一度把计数键改成 `(IP, 用户名)` 并豁免回环/私网；v1.0.4 按实际使用反馈调整回**纯来源 IP**：

- 计数键就是来源 IP，**不区分用户名**——同一 IP 换个用户名再试不会「洗掉」计数；
- **默认不豁免任何来源**：回环与私网同样受限流保护，局域网部署下锁定真正生效
  （v1.0.3 的豁免导致局域网内永远看不到锁定，功能等于没开）；
- 需要放行特定网段时，把前缀写进 `LOGIN_LOCK_TRUSTED_PREFIXES`（默认空元组），
  例如 `('127.', '192.168.')`。适合前置反向代理把所有人收敛成一个 IP 的部署。

> ⚠️ **取舍说明**：纯 IP 粒度意味着共享出口 IP（反向代理 / NAT）时，
> 一个人失败 5 次会连带锁掉同 IP 的所有人——这正是第三轮报告 A-01 描述的场景。
> 本次是**有意识地接受**这一取舍，换取局域网内锁定真实可用。
> 如果部署在反向代理之后，请把代理出口 IP 加进 `LOGIN_LOCK_TRUSTED_PREFIXES`，
> 或者干脆在代理层做限流。

**连续失败窗口（v1.0.4 新增）**

`LOGIN_FAIL_WINDOW = 120`：两次失败之间只要超过 120 秒没有新失败，计数就清零重来。
没有这个窗口时，隔几天累计 5 次失败也会被锁，属于误伤正常用户。

**二维码为什么要走同源代理（v1.0.3）**

二维码由草料开放平台公开接口生成（`https://api.2dcode.biz/v1/create-qr-code`）。
该接口的 CORS 策略是**只对 `localhost` / `127.0.0.1` 回 `Access-Control-Allow-Origin`**，
所以从局域网 IP 或域名访问时，浏览器里的 `fetch` 必然被拦——**「打包下载 zip」在任何真实
部署上都必然降级**（实测：NAS 上 zip 下载超时，落到 `window.open` 兜底）。
现在前端改请求同源的 `/qr`，由服务端转发：

- 上游主机写死在代码里（请求参数无法指定地址，杜绝 SSRF）；
- `data` / `size` 严格校验后用 `urlencode` 拼装（杜绝参数注入），响应限类型、限体积；
- 服务端按 `(data, size)` 做进程内缓存，同一张图不重复回源；
- 代理不可用时（静态部署、NAS 无外网）前端自动回落到直连 `<img>`，不至于整页开天窗。

**为什么把界面打包进去**

桌面入口 `type=url` 指向服务自身端口，前端页面、图标都在 `app/ui/` 里，
所以这个应用**只依赖 NAS 本地**，不依赖外部站点存活。

**安全响应头（v1.0.3）**

所有响应都带 `CSP` / `X-Frame-Options: DENY` / `Referrer-Policy: no-referrer` /
`X-Content-Type-Options: nosniff` / `Cross-Origin-Opener-Policy: same-origin`。
CSP 的 `connect-src` 收紧为 `'self'`（二维码走同源代理，不再需要放行第三方域）；
`img-src` 保留第三方域，是为了让代理不可用时的直连回落还能用。
桌面入口是**新窗口**打开而非内嵌 iframe（已实测），所以 `frame-ancestors 'none'` 不影响入口。

**请求层防护（v1.0.3）**

- `HTTP/0.9` 简写请求（无版本号）→ `505` 后断开（原来会被正常处理）
- 单行请求头超过 8 KB → `431`（原来是被静默丢弃）
- `Host` 缺失或含异常字符 → `400`
- `POST` body 超过 64 KB → `413`（原来是静默截断）
- 第三方脚本 `JSZip` 补上 `integrity`（SRI）+ `crossorigin`

## 已知限制与注意事项

1. **依赖系统 Python3**：需要 3.6+（飞牛自带 `/usr/bin/python3` 3.11）。
   `install_init` 会先检查，缺失则在安装阶段就失败并给出提示。
2. **端口占用检查**：v1.0.1 起 `checkport = false`。应用中心启动前**不会**再拿 manifest
   里那个静态 `service_port` 去判断占用——它不跟随你改的端口，开着只会误报
   「端口被占用」。真实的端口冲突会体现为服务端绑定失败，
   日志在 `$TRIM_PKGVAR/app.log`（`Address already in use`），换个空闲端口即可。
   早期 1.0.0 版本在 **10001 已被别的服务占用**的机器上，会出现
   「不管把访问端口改成什么都提示端口被占用」——升级到 1.0.1 即可解决
   （需要按「卸载 → 重新安装」的方式换包）。
3. **不要用 CSV/命令行卸载带向导的应用**，会提示改从 Web UI 卸载。
4. **二维码内容不落盘**：只在浏览器和草料开放平台公开接口之间流转，服务端只做静态托管与鉴权。
5. 升级路径：飞牛当前对第三方应用按「卸载 → 重新安装」处理；`upgrade_*` 脚本已实现，
   且升级不会覆盖你改过的端口与认证设置。
6. **登录锁定记在进程内存里**：重启应用（或在应用中心停用再启用）会清空失败计数。
   这是刻意的取舍——不写盘就不需要考虑运行用户的写权限，代价是防不住「重启应用来解锁」。
   真要防暴力破解，建议在网络层（路由 / 反代）另做限制。
7. **倒计时是纯前端显示**：秒数按页面打开时刻服务端给出的剩余值递减，不做轮询。
   真实判定始终在服务端（`do_POST` 每次都会查 `blocked()`），所以即使页面
   倒计时被跳过，请求照样会被拒绝。
8. **登录锁定按来源 IP，且不豁免内网**（v1.0.4）：回环与私网来源同样受限流保护，
   所以局域网内**能**看到锁定效果（v1.0.3 曾豁免私网，导致功能在局域网内等于没开）。
   代价是**共享出口 IP 时，一个人失败 5 次会连带锁掉同一 IP 的所有人**
   （反向代理 / NAT 场景，即第三轮报告 A-01 描述的情形）——这是本次**有意接受**的取舍。
   若部署在反向代理之后，请把代理出口 IP 加进 `LOGIN_LOCK_TRUSTED_PREFIXES`，或在代理层限流。
9. **二维码接口依赖第三方**：`api.2dcode.biz` 是公开接口，无 SLA、可能变更限额或下线。
   v1.0.3 起由服务端转发（`/qr`），所以**NAS 需要能访问外网**才能出码；
   若 NAS 无外网，前端会回落到浏览器直连（要求客户端能上外网）。
10. **会话与限流状态都在进程内存里**：重启应用即清空（包括登出吊销表）。
    这是「不写配置目录、不依赖运行用户写权限」换来的，属刻意取舍。

## 排错速查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 启用时提示「端口被占用」，换端口也一样 | 1.0.0 的 manifest 写死 `service_port = 10001`，而应用中心的检查只认这个字段 | 换 1.0.1（`checkport = false`） |
| 启用成功但页面打不开 | 端口真的被别的服务占了，服务端绑定失败 | 看 `$TRIM_PKGVAR/app.log`，换空闲端口后重新启用 |
| 应用中心显示已停用，但端口还占着 | 曾在应用中心之外手工起过进程 | 结束该进程，或从应用中心重新启用 |
| 登录提示「失败次数过多」，等待后仍是同一秒 | 1.0.0/1.0.1 的倒计时是静态渲染，且锁定期内每次提交都会重置窗口 | 换 1.0.2；着急用时重启应用可清空计数 |
| 被锁定后想立刻登录 | `LoginGuard` 是进程内状态 | 应用中心「停用 → 启用」，等价于清空计数 |
| 局域网内怎么都触发不了锁定 | v1.0.3 曾把回环与私网来源加入 `LOGIN_LOCK_TRUSTED_PREFIXES` | 升级到 v1.0.4，该豁免已取消 |
| 自己输错几次就把自己锁了 | v1.0.4 起按来源 IP 锁定且不再豁免内网 | 预期行为；等 120 秒，或「停用 → 启用」清空计数。多人共用出口 IP 时把该 IP 加进 `LOGIN_LOCK_TRUSTED_PREFIXES` |
| 提交登录后提示「表单已过期」 | 登录页停留超过 30 分钟，一次性 CSRF 令牌失效 | 刷新登录页重新获取令牌即可 |
| 「打包下载」没反应 / 浏览器控制台报 CORS | 1.0.3 之前前端直连第三方接口，而它只对 localhost 放行 CORS | 换 1.0.3（改走同源 `/qr` 代理） |
| 出码全部失败、页面提示检查网络 | 服务端与客户端都上不了外网 | 确认 NAS 能访问 `api.2dcode.biz`（`/qr` 日志里有 `upstream failed`） |
| 桌面图标点开是空白页 | 1.0.3 起带 `X-Frame-Options: DENY`，若被第三方页面内嵌会拒绝渲染 | 直接访问 `http://<NAS>:<端口>/`；本应用的桌面入口是新窗口打开，不受影响 |
